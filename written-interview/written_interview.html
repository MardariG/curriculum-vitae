What are the key things to think about in regard to architecture, maintainability, and reliability in these large systems?

  • Clear contracts between components. Well-designed REST APIs (or GraphQL schemas) are the real architecture of a multi-service system. They should be explicit, versioned, documented and typed end to end, so the front end and back end can evolve independently.
  • Clear ownership and boundaries. Each service and each front-end module should have one clear responsibility and owner. Shared component libraries such as a design system remove duplication without coupling teams' release cycles.
  • Designing for failure. In distributed systems something is always failing somewhere. The UI needs explicit loading, empty, error and partial states. Back ends need timeouts, retries with backoff, and idempotent operations. In payments, idempotency is what stops a retried request from becoming a double payment.
  • Data consistency and caching. Decide deliberately where the source of truth is, how stale data may be, and how the client cache is invalidated, especially for real-time data.
  • Observability. Logging, metrics, tracing and front-end error reporting, so that issues are found by the team before customers report them.
  • Automated testing at the right levels. Unit tests for logic, component tests for UI behaviour, contract tests between services, and a small set of end-to-end tests for critical user journeys.
  • Safe delivery. CI/CD, code review, feature flags and the ability to roll back quickly. Small, frequent releases are less risky than big ones.
  • Simplicity and consistency. Shared conventions, linting and documented decisions make a large codebase readable for the next engineer. I learned this when I set the patterns for the Fiserv application, which the rest of the team then followed.

Outline your views on the role of an engineering manager in shaping a high-functioning team.

I think a good engineering manager mostly creates the conditions in which good engineers can do their best work:

  • Clarity. Everyone should know what we are building, why it matters to the user, and what "done" means. Most team friction comes from unclear goals, not from bad engineers.
  • Psychological safety. People must feel safe to say "I don't understand", "I made a mistake" or "I think this design is wrong". As a Dev Lead I try to show this myself, for example by admitting openly when I am not sure.
  • Removing blockers. The manager's time is well spent unblocking others: getting a decision from product, clarifying an API with another team, or protecting focus time.
  • Growth. Regular honest feedback, stretch tasks matched to each person, and mentoring. Teams stay strong when people can see themselves progressing.
  • High standards, shared by everyone. Code review, testing and accessibility should be team habits, not personal preferences. The manager sets the bar and makes it easy to meet.
  • Healthy delivery rhythm. Sustainable pace, small increments, and blameless retrospectives after incidents so the team learns instead of hiding problems.
  • Hiring and team composition. Hiring for ability, curiosity and communication, and building a team with complementary strengths.

Outline your thoughts on performance in software engineering. How do you ensure that your product is fast?

Performance is a feature that users feel even when they cannot name it. My approach is to measure, set budgets, and keep it fast continuously instead of fixing it once.

  • Measure first: Chrome DevTools performance profiles, the React Profiler, Lighthouse and Core Web Vitals (LCP, INP, CLS), and on mobile, frame rates and cold-start time. I don't optimise on assumptions.
  • Ship less code: code splitting and lazy loading per route, tree-shaking, avoiding heavy dependencies, and watching bundle size in CI.
  • Render less: correct memoisation boundaries, stable references, normalised state, selectors, and virtualised lists for large data sets. In React Native these techniques plus Hermes and Reanimated are what made 60fps interactions possible.
  • Fetch smarter: pagination, caching and request de-duplication (e.g. Apollo cache), avoiding waterfalls, and good API design. A well-shaped REST endpoint is often the biggest performance improvement.
  • Perceived performance: skeletons, optimistic updates and progressive rendering, so the interface responds immediately.
  • CSS and assets: modern layout instead of JavaScript-driven layout, optimised images and fonts, and avoiding layout thrashing.
  • Guard against regressions: performance budgets and checks in CI, so the product stays fast as the team adds features.

Outline your thoughts on quality in software development. What practices are most effective in software teams to drive improvements in quality?

Quality is not a phase at the end. It is the result of many small habits that the whole team shares. The practices I have seen work best:

  • Thoughtful code review focused on correctness, readability and design, not just style. Linters and formatters (ESLint, Prettier) should handle style automatically so humans can focus on what matters.
  • Strong typing: TypeScript catches a whole class of bugs before they exist, especially at API boundaries.
  • A balanced test suite: fast unit and component tests (Jest, Testing Library), and end-to-end tests (Cypress) for critical journeys. On Cisco Webex I covered critical user flows with Cypress, which gave the team confidence to refactor.
  • CI that blocks merges on failing tests, lint or type errors, and small pull requests that are easy to review.
  • Design systems: reusable, accessible, well-tested components mean each bug is fixed once, for every product.
  • Accessibility as part of the definition of done: semantic HTML, keyboard navigation, screen-reader checks and contrast are quality issues, not extras.
  • Close collaboration with QA and design from the start, so requirements and edge cases are clear before coding begins. In payments, edge cases are where the real bugs live.
  • Learning from incidents: blameless post-mortems and turning every production bug into a regression test.
  • Paying down technical debt deliberately, as I did at Mastercard, instead of letting it accumulate until it blocks delivery.

4. Context

Outline your thoughts on the mission of Canonical. What is it about the company's purpose and goals which is most appealing to you? What is risky or unappealing? Are there any elements of the company goals that you are unsure about?

As I understand it, Canonical's mission is to make open-source software secure, reliable and easy to use for everyone, from a single developer's laptop to the largest clouds, data centres and edge devices, and to fund that work sustainably through enterprise support and services. Ubuntu is the visible part of the mission. Behind it are long-term security maintenance, cloud and Kubernetes tooling, IoT, and the web products that let people discover, install and manage all of this.

What appeals to me most is that the work is open and has very wide reach. Improvements made here are used by millions of people and organisations, not only one client. As a front-end engineer I find the Vanilla Framework especially meaningful: a shared, accessible presentation layer that brings consistency to Canonical's products and can be adopted by other open-source projects that often have no designers or front-end specialists. Accessibility done well in a shared toolkit spreads to every product built on it. I also like that Canonical treats design as engineering's partner.

What I see as risky: Canonical competes against companies with much larger budgets while also giving much of its work away for free. That requires very careful focus. Some product decisions (Snap, for example) have caused friction with parts of the community, and being both a community steward and a commercial vendor is a difficult balance. The globally distributed, remote-first model with a demanding bar is a great strength, but it also needs excellent written communication and discipline. I see that as a challenge I would enjoy rather than a negative.

What I am unsure about: the long-term role of Flutter. It is a promising way to unify desktop and web, but it depends heavily on Google's continued investment, and Flutter on the web still has trade-offs in accessibility, SEO and bundle size compared with React. I would like to understand how Canonical decides which products should be built in Flutter and which stay in React.

Who are competitors to Canonical, and what does Canonical need to change to be a more effective competitor?

  • Enterprise Linux: Red Hat (IBM) with RHEL and OpenShift, SUSE, and community rebuilds such as Rocky Linux and AlmaLinux.
  • Cloud providers' own platforms: Amazon Linux, Azure Linux, Google's Container-Optimized OS, and managed Kubernetes services that reduce the need for a separately supported OS.
  • Developer desktop: macOS and Windows with WSL, which, ironically, often runs Ubuntu.
  • Private cloud and infrastructure: VMware (Broadcom) and Nutanix, and Red Hat OpenShift for Kubernetes.
  • Secure container images and supply chain: companies like Chainguard and Docker's hardened images.

To compete more effectively, I think Canonical should:

  • Make the web experience of its products as polished and self-service as the best SaaS: clear docs, fast and accessible dashboards, simple trial and purchase flows. Enterprise buyers often judge a platform by its interfaces first. This is where web engineering has direct commercial impact.
  • Communicate its security and long-term support value more clearly, especially in the current climate around Red Hat's source policies and VMware's licensing changes, which are opportunities to win customers.
  • Keep strengthening community trust through openness about decisions such as Snap, so developers stay advocates.
  • Grow the Vanilla Framework outside Canonical, with strong documentation, React components and examples, so that it becomes a recognised open-source design system and a channel to developers.
