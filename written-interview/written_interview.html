Describe your experience building large systems with many services – web front ends, REST APIs, data stores, event processing and other kinds of integration between components.

Most of my professional work has been building the front ends of large, multi-service systems, where the UI is the place in which many back-end services meet:

  • Adobe Workfront (Document Management): upload, preview, versioning and approval of creative assets inside enterprise workflows. These features depend on several services (storage, preview generation, versioning, permissions and workflow), and the UI must handle long-running asynchronous operations and partial failures gracefully.
  • Mastercard: a payments management suite with a GraphQL/Apollo data layer over payment, account, user and user-group services, plus an admin layer for payment settings. The dynamic form engine was configuration-driven, so the front end had to stay correct for every client configuration.
  • Fiserv: a payments application for creating, viewing and modifying internal and external payments over REST APIs, which I built from the first commit.
  • Western Union: a merchant portal for small and medium enterprises with single and multiple points of sale, aggregating transaction and account data.

In my own products I own the whole stack. For my bill-splitting app, which is live on the web, Android and iOS, I designed and built the REST API in Node.js with TypeScript over a relational database. Some examples of the API design decisions:

  • Resource-oriented endpoints such as GET /groups/{id}/bills, POST /groups/{id}/bills and GET /groups/{id}/balances, with consistent naming, HTTP verbs and status codes.
  • Idempotency keys on POST requests, so that a mobile client retrying on a bad connection never creates the same bill twice. This is a lesson I brought from payments.
  • Cursor-based pagination for bill history, and a single, consistent error format (code, message, field details) that every client can display properly.
  • Money stored as integer minor units with an explicit currency, never as floating point, and balances calculated on the server so that the web and mobile clients always agree.
  • Versioned API (/v1) and shared TypeScript types, so mobile apps already installed on users' phones keep working while the API evolves.
  • Authentication with short-lived access tokens and refresh tokens, and authorisation checked on every request, so a user can only access groups they belong to.

For event-driven integration, my crypto app consumes real-time market data over WebSockets, merges it with REST history endpoints, and triggers push notifications when a price alert condition is met. On the server side, slow work such as sending notifications runs in background jobs rather than inside the request, so the API stays fast.

What are the key things to think about in regard to architecture, maintainability, and reliability in these large systems?

  • Clear contracts between components. Well-designed REST APIs (or GraphQL schemas) are the real architecture of a multi-service system. They should be explicit, versioned, documented and typed end to end, so the front end and back end can evolve independently.
  • Clear ownership and boundaries. Each service and front-end module should have one clear responsibility and owner. Shared component libraries such as a design system remove duplication without tying teams' release cycles together.
  • Designing for failure. In a distributed system something is always failing somewhere. The UI needs explicit loading, empty, error and partial states. Back ends need timeouts, retries with backoff, and idempotent operations. In payments, idempotency is what prevents a retried request from becoming a double payment.
  • Data consistency and caching. Decide deliberately where the source of truth is, how stale data may be, and how client caches are invalidated, especially for real-time data.
  • Asynchronous work and events. Move slow or unreliable work into queues and background jobs, make consumers idempotent, and plan for events arriving late, twice or out of order.
  • Observability. Logging, metrics, tracing and front-end error reporting, so the team finds issues before customers report them.
  • Automated testing at the right levels. Unit tests for logic, component tests for UI behaviour, contract tests between services, and a small set of end-to-end tests for critical user journeys.
  • Safe delivery. CI/CD, code review, feature flags and fast rollback. Small, frequent releases are less risky than big ones.
  • Simplicity and consistency. Shared conventions, linting and documented decisions make a large codebase readable for the next engineer. I learned this when I set the patterns for the Fiserv application, which the rest of the team then followed.

One example of leadership I am proud of: on Workfront, users with very large folders reported that the document list became slow and sometimes froze when they selected or filtered assets. I took ownership of the investigation. Profiling with the React Profiler showed that each selection re-rendered the entire list, because a Redux selector returned a new array on every state change and some row components received new callback references each time. Together with one of the developers I was mentoring, we introduced memoised selectors, stabilised the callbacks, split each row into a memoised component, and virtualised the list so only the visible rows were rendered. Selection and filtering in large folders became instant, and the related customer complaints stopped. Just as important, we turned the lessons into code-review guidelines and a short session for the team, so the same problem does not return in other parts of the product.

Outline your views on the role of an engineering manager in shaping a high-functioning team.

I think a good engineering manager mostly creates the conditions in which good engineers can do their best work:

  • Clarity. Everyone should know what we are building, why it matters to the user, and what "done" means. Most team friction comes from unclear goals, not from bad engineers.
  • Psychological safety. People must feel safe to say "I don't understand", "I made a mistake" or "I think this design is wrong". I try to show this myself as a lead, for example by saying openly when I am not sure about something.
  • Removing blockers. The manager's time is well spent unblocking others: getting a decision from product, clarifying an API with another team, or protecting focus time.
  • Growth. Regular honest feedback, stretch tasks matched to each person, and mentoring. Teams stay strong when people can see themselves progressing.
  • High standards, shared by everyone. Code review, testing and accessibility should be team habits, not personal preferences. The manager sets the bar and makes it easy to meet.
  • Healthy delivery rhythm. Sustainable pace, small increments, and blameless retrospectives after incidents, so the team learns instead of hiding problems.
  • Hiring and team composition. Hiring for ability, curiosity and communication, and building a team with complementary strengths.
  • A positive culture. Energy and optimism are contagious, especially under pressure. I have always been the person who stays positive and supportive when things are difficult, and I have seen how much that helps a team keep focus and recover from setbacks.

Outline your thoughts on performance in software engineering. How do you ensure that your product is fast?

Performance is a feature that users feel even when they cannot name it. My approach is to measure, set budgets, and keep it fast continuously instead of fixing it once.

  • Measure first: Chrome DevTools performance profiles, the React Profiler, Lighthouse and Core Web Vitals (LCP, INP, CLS), and on mobile, frame rates and cold-start time. I don't optimise based on assumptions.
  • Ship less code: code splitting and lazy loading per route, tree-shaking, avoiding heavy dependencies, and watching bundle size in CI. This matters even more for Flutter on the web, where the initial download is a key cost.
  • Render less: correct memoisation boundaries, stable references, normalised state, memoised selectors, and virtualised lists for large data sets. The Workfront document-list example above is a typical case. In React Native, the same techniques plus Hermes and Reanimated are what made 60fps interactions possible.
  • Fetch smarter: pagination, caching and request de-duplication, avoiding request waterfalls, and good API design. A well-shaped REST endpoint that returns exactly what the screen needs is often the biggest performance improvement.
  • Fast back ends: proper database indexes, avoiding N+1 queries, and moving slow work into background jobs.
  • Perceived performance: skeletons, optimistic updates and progressive rendering, so the interface responds immediately.
  • CSS and assets: modern layout instead of JavaScript-driven layout, optimised images and fonts, and avoiding layout thrashing.
  • Guard against regressions: performance budgets and checks in CI, so the product stays fast as the team adds features.

Outline your thoughts on quality in software development. What practices are most effective in software teams to drive improvements in quality?

Quality is not a phase at the end. It is the result of many small habits shared by the whole team. The practices I have seen work best:

  • Thoughtful code review focused on correctness, readability and design, not just style. Linters and formatters should handle style automatically so people can focus on what matters.
  • Strong typing: TypeScript and Dart catch a whole class of bugs before they exist, especially at API boundaries.
  • A balanced test suite: fast unit and component tests, plus end-to-end tests for critical journeys. On Cisco Webex I covered critical user flows with Cypress, which gave the team confidence to refactor.
  • CI that blocks merges on failing tests, lint or type errors, and small pull requests that are easy to review.
  • Design systems: reusable, accessible, well-tested components mean each bug is fixed once, for every product.
  • Accessibility as part of the definition of done: semantic HTML, keyboard navigation, screen-reader checks and contrast are quality issues, not extras.
  • Close collaboration with QA and design from the start, so requirements and edge cases are clear before coding begins. In payments, edge cases are where the real bugs live.
  • Responsible use of AI tools: AI-generated code is reviewed and tested exactly like human code. AI can also raise quality by generating test cases and spotting edge cases a reviewer might miss.
  • Learning from incidents: blameless post-mortems, and turning every production bug into a regression test.
  • Paying down technical debt deliberately, as I did at Mastercard, instead of letting it accumulate until it blocks delivery.

4. Context

Outline your thoughts on the mission of Canonical. What is it about the company's purpose and goals which is most appealing to you? What is risky or unappealing? Are there any elements of the company goals that you are unsure about?

As I understand it, Canonical's mission is to make open-source software secure, reliable and easy to use for everyone, from a single developer's laptop to the largest clouds, data centres and edge devices, and to fund that work sustainably through enterprise support and services. Ubuntu is the visible part of the mission. Behind it are long-term security maintenance, cloud and Kubernetes tooling, IoT, and the web products that let people discover, install and manage all of this.

What appeals to me most is that the work is open and has very wide reach. Improvements made here are used by millions of people and organisations, not only one client. As a front-end engineer I find the Vanilla Framework especially meaningful: a shared, accessible presentation layer that brings consistency to Canonical's products and can be adopted by other open-source projects that often have no designers or front-end specialists. Accessibility done well in a shared toolkit spreads to every product built on it. I also like that Canonical treats design as a partner of engineering, and that it is investing in Flutter, a technology I already use and believe in.

What I see as risky: Canonical competes against companies with much larger budgets while also giving much of its work away for free. That requires very careful focus. Some product decisions, such as Snap, have caused friction with parts of the community, and being both a community steward and a commercial vendor is a difficult balance. The globally distributed, remote-first model with a demanding bar is a great strength, but it needs excellent written communication and self-discipline. I see that as a challenge I would enjoy rather than a negative.

What I am unsure about: the long-term role of Flutter on the web. From my own experience, Flutter is excellent for unifying mobile and desktop, but on the web it still has trade-offs in initial load size, SEO and accessibility compared with React. It also depends on Google's continued investment. I would like to understand how Canonical decides which products should be built in Flutter and which should stay in React.

Who are competitors to Canonical, and what does Canonical need to change to be a more effective competitor?

  • Enterprise Linux: Red Hat (IBM) with RHEL and OpenShift, SUSE, and community rebuilds such as Rocky Linux and AlmaLinux.
  • Cloud providers' own platforms: Amazon Linux, Azure Linux, Google's Container-Optimized OS, and managed Kubernetes services that reduce the need for a separately supported operating system.
  • Developer desktop: macOS (which I use myself) and Windows with WSL, which, ironically, often runs Ubuntu.
  • Private cloud and infrastructure: VMware (Broadcom) and Nutanix, and Red Hat OpenShift for Kubernetes.
  • Secure container images and the software supply chain: companies such as Chainguard, and Docker's hardened images.

To compete more effectively, I think Canonical should:

  • Make the web experience of its products as polished and self-service as the best SaaS products: clear docs, fast and accessible dashboards, and simple trial and purchase flows. Enterprise buyers often judge a platform by its interfaces first, and this is where web engineering has direct commercial impact.
  • Communicate its security and long-term support value more clearly, especially now, when Red Hat's source policy and VMware's licensing changes are pushing customers to look for alternatives.
  • Win over more developers on macOS and Windows, for example through excellent WSL, container and virtual-machine experiences, so Ubuntu stays the default wherever developers work.
  • Keep strengthening community trust through openness about decisions such as Snap, so developers remain advocates.
  • Grow the Vanilla Framework outside Canonical, with strong documentation, React components and examples, so it becomes a recognised open-source design system and a channel to developers.

From the outside, I would most like Canonical's design and front-end work to become more visible to the wider developer community.
